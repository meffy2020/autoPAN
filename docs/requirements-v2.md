# autoPAN v2 요구사항 및 운영 설계

## 1. 목적

autoPAN v2는 노원청소년센터 나놀다판의 현장 운영을 단순화하기 위한 내부 운영 시스템이다.

학생과 보호자는 태블릿 키오스크에서 접수만 하고, 직원은 관리자 화면에서 결제 확인, 자리 배정, 시작, 종료, 연장을 처리한다. 데이터베이스와 서버는 사용자가 직접 다루지 않는다. 운영자는 브라우저 화면만 사용한다.

## 2. 운영 전제

### 2.1 현장 구성

- 서버: Windows 노트북 1대
- 네트워크: 전용 공유기 기반 내부망
- 학생 단말: 태블릿 브라우저
- 직원 단말: 데스크톱 또는 노트북 브라우저
- 보드 화면: 필요할 경우 별도 브라우저 화면
- 외부 클라우드: 사용하지 않음
- 외부 결제 연동: 사용하지 않음

### 2.2 접속 주소

서버 노트북은 전용 공유기에서 고정 IP를 받는다. 모든 화면은 같은 내부망에서 서버 IP로 접속한다.

```text
태블릿 키오스크: http://SERVER_IP:3000/kiosk
직원 관리자:     http://SERVER_IP:3000/admin
대기 보드:       http://SERVER_IP:3000/board
```

### 2.3 운영자 지식 수준

운영자는 다음을 몰라도 시스템을 사용할 수 있어야 한다.

- SQL
- 데이터베이스 테이블 구조
- 터미널 명령어
- Node.js 실행 방식
- 서버 로그 분석
- 백업 명령어

운영자에게 필요한 작업은 브라우저 화면의 버튼, 검색, 선택, 저장으로 끝나야 한다.

## 3. 핵심 원칙

### 3.1 DB는 숨긴다

관리자는 데이터베이스를 보지 않는다. 관리자는 업무 상태를 본다.

```text
나쁜 방향: members, visits, queue_entries 테이블을 직접 보여준다.
좋은 방향: 오늘 접수, 대기, 결제 대기, 이용 중, 일마감으로 보여준다.
```

### 3.2 업무 단어를 쓴다

화면에는 DB 용어보다 현장 단어를 사용한다.

| DB 용어 | 화면 용어 |
| --- | --- |
| `members` | 회원 / 학생 |
| `visits` | 접수 |
| `queue_entries` | 대기 |
| `sessions` | 이용 중 |
| `payments` | 결제 기록 |
| `resources` | 자리 / 기기 |
| `pricing_rules` | 시간권 / 연장권 |
| `daily_operation_reports` | 일별 기록 |
| `staff_activity_logs` | 운영 기록 |

### 3.3 실수 복구가 가능해야 한다

운영자는 실수할 수 있다. 시스템은 실수를 전제로 설계한다.

- 삭제보다 취소, 노쇼, 종료 같은 상태 변경을 우선한다.
- 중요한 버튼은 확인 단계를 둔다.
- 결제, 시작, 종료, 노쇼, 재대기는 운영 기록에 남긴다.
- 잘못 누른 작업을 추적할 수 있게 직원 이름과 시각을 저장한다.

### 3.4 서버 운영은 자동화한다

운영자는 매일 서버 명령어를 치지 않는다.

- Windows 시작 시 앱 자동 실행
- 서버 노트북 절전 방지
- 방화벽 포트 자동 또는 문서화된 1회 설정
- 매일 자동 백업
- 관리자 화면에서 서버/DB/백업 상태 확인

### 3.5 모든 화면은 내부망 다중 단말을 전제로 한다

개발 중에는 Mac 로컬 서버에서 확인하더라도, 최종 운영은 Windows 노트북 서버에 태블릿과 직원 데스크톱이 접속하는 구조다.

- 화면은 같은 내부망의 여러 브라우저에서 동시에 열릴 수 있어야 한다.
- 키오스크, 관리자, 보드는 같은 서버 상태를 봐야 한다.
- 관리자 화면은 데스크톱 모니터 전용으로 설계한다. 태블릿이나 모바일 최적화보다 넓은 화면에서의 빠른 운영성을 우선한다.
- 태블릿 키오스크는 터치 중심, 관리자 화면은 빠른 마우스 조작 중심으로 설계한다.
- 운영 중 새로고침해도 현재 상태를 즉시 복구해야 한다.

### 3.6 관리자 화면은 빠른 업무 수행을 우선한다

관리자 화면은 많은 정보를 한 번에 보여주는 것보다, 지금 해야 할 작업을 바로 찾고 실행하는 것을 우선한다.

- 대기 인원은 자원별로 한눈에 보여야 한다.
- 결제 대기, 호출됨, 대기 중, 빈자리 수를 분리해서 보여야 한다.
- 자주 쓰는 작업은 접힌 영역 안에 숨기지 않는다.
- 예외 작업만 접힌 영역이나 보조 버튼으로 둔다.
- 자리 고장, 자리 교체 같은 현장 상황은 별도 복잡한 절차 없이 바로 처리해야 한다.

## 4. 화면 설계

### 4.1 `/kiosk` 학생 접수 화면

목적: 학생 또는 보호자가 스스로 접수한다.

포함 기능:

- 재방문 회원 검색
- 첫 방문 회원 등록
- PC / 닌텐도 / 플레이스테이션 / 공간 이용 선택
- 시간권 선택
- 접수 완료 안내
- 30초 무반응 시 첫 화면 복귀

제외 기능:

- 결제 처리
- 자리 직접 선택
- 관리자 메뉴
- 전체 회원 목록 노출
- 운영 설정 변경

### 4.2 `/admin` 직원 운영 화면

목적: 직원이 오늘 운영을 처리한다.

관리자 화면은 데스크톱 모니터 전용 운영판으로 설계한다. 자주 쓰는 기능은 탭 이동 없이 한 화면에서 처리하고, 회원/일마감/설정/유지보수 같은 보조 기능만 별도 영역이나 보조 화면으로 분리한다.

- 대기 수
- 서버 상태
- DB 상태
- 마지막 백업 시각
- 자원별 대기 요약
- 자원별 결제 대기 수
- 자원별 호출됨 수
- 자원별 빈자리 수
- PC 대기열
- 닌텐도 대기열
- 플레이스테이션 대기열
- 다음 처리 대상 표시
- 호출하기
- 노쇼 처리
- 다시 대기 넣기
- 결제 대기 학생 목록
- 선택한 시간권과 결제 금액
- 현금 / 카드 선택
- 결제 완료 기록
- 빈 자리 배정
- 이용 시작
- 자리별 사용 상태
- 학생 이름 또는 호출 번호

- 종료 임박 표시
- 자리 이동
- 연장
- 종료

권장 배치:

```text

왼쪽: 다음 처리 대상과 결제 후 시작

좌석 클릭: 해당 좌석 위 작업 패널에서 자리 이동 / 연장 / 종료
오른쪽: 대기 처리와 마감 요약
```

### 4.3 `/maintenance` 유지보수 화면

목적: 개발자 또는 관리 책임자가 드물게 사용한다.

일반 직원 화면과 분리한다. 접근에는 별도 PIN을 둔다.

포함 기능:

- 백업 파일 다운로드
- 수동 백업 실행
- 백업 복구 안내
- 운영 로그 조회
- 앱 버전 확인
- DB 연결 상태 확인
- 네트워크 접속 주소 확인

제외 기능:

- 학생이 접근 가능한 링크 노출
- 원본 테이블 직접 수정
- 임의 SQL 실행

## 5. 데이터 설계

### 5.1 저장소 선택

현장 v2의 우선 선택은 SQLite 파일 저장이다.

이유:

- Windows 노트북에서 설치와 운영이 단순하다.
- 별도 DB 서버 프로세스가 필요 없다.
- 백업이 파일 복사 중심이라 운영자가 이해하기 쉽다.
- 현재 규모에서는 동시 접속과 데이터량이 작다.

PostgreSQL은 다음 조건에서 전환한다.

- 여러 센터를 통합 운영한다.
- 동시 쓰기 부하가 커진다.
- 전문 운영자가 DB 백업과 복구를 담당한다.
- 장기간 운영 데이터 분석 요구가 커진다.

### 5.2 핵심 데이터

| 데이터 | 저장 내용 | 화면에서 쓰는 곳 |
| --- | --- | --- |
| 회원 | 이름, 학년/나이, 보호자 연락처, 메모 | 키오스크 검색, 관리자 회원 |
| 자원 | PC/Nintendo/PS 자리 목록 | 관리자 현재 이용, 자리 배정 |
| 요금 | 시간권, 연장권, 금액 | 키오스크 시간 선택, 결제 |
| 접수 | 방문 단위, 티켓번호, 상태 | 오늘 운영, 결제 대기 |
| 대기 | 자원별 대기 순서, 호출 상태 | 대기 / 호출 |
| 이용 | 자리, 시작/종료 예정, 연장 | 현재 이용 |
| 결제 | 금액, 결제수단, 기록 직원 | 일마감, 결제 기록 |
| 일별 기록 | 날짜, 중복 제외 방문 인원, 접수 수, 자원별 매출, 총매출 | 기록 / 리포트 |
| TTS | 호출/종료 안내 메시지 | 보드, 운영 기록 |
| 운영 로그 | 직원, 행동, 대상, 시각 | 유지보수, 감사 추적 |
| 설정 | 호출 방식, 알림 시간, 직원 목록 | 설정 |

### 5.3 상태 흐름

유료 콘텐츠의 기본 흐름은 다음과 같다.

```text
접수
  -> 결제 대기
  -> 결제 완료
  -> 자리 배정
  -> 이용 중
  -> 종료
```

대기가 있을 때는 다음 흐름을 탄다.

```text
접수
  -> 대기 중
  -> 호출됨
  -> 결제 대기
  -> 결제 완료
  -> 자리 배정
  -> 이용 중
  -> 종료
```

공간 이용은 유료 콘텐츠 흐름에 들어가지 않는다.

```text
접수
  -> 공간 이용 기록 완료
```

## 6. 관리자에게 보이는 DB 구성

관리자 화면은 원본 테이블이 아니라 업무용 집계와 목록을 제공한다.

### 6.1 오늘 운영용 데이터

관리자 첫 화면은 다음 데이터만 요약해서 보여준다.

- 오늘 접수 수
- 현재 이용 중 수
- 대기 중 수
- 호출됨 수
- 결제 대기 수
- 오늘 매출
- 마지막 백업 시각
- 서버 상태

### 6.2 결제 대기 목록

각 항목은 다음 형태로 보여준다.

```text
김하늘 / PC / 60분 / 1,000원
[현금] [카드] [결제 완료 후 시작]
```

내부적으로는 `visits`, `members`, `pricing_rules`, `payments`, `sessions`가 연결되지만 관리자는 이 구조를 보지 않는다.

### 6.3 현재 이용 목록

각 항목은 다음 형태로 보여준다.

```text
PC-01 / 김하늘 / 남은 18분
[자리 이동] [연장] [종료]
```

내부적으로는 `sessions`, `resources`, `visits`, `members`가 연결된다.

### 6.4 자리 이동

자리 이동은 현재 이용 중인 세션의 자원만 바꾸는 작업이다. 이용 시작 시각, 종료 예정 시각, 결제 기록은 유지한다.

예시:

```text
PC-01 / 지우 / 남은 42분
PC-01 고장 -> PC-02로 이동
```

처리 규칙:

- 같은 자원 종류 안에서만 이동할 수 있다. PC 이용자는 PC 자리로만 이동한다.
- 이미 사용 중인 자리로는 이동할 수 없다.
- 비활성 자리로는 이동할 수 없다.
- 이동 전 자리와 이동 후 자리를 운영 로그에 남긴다.
- 학생에게 다시 접수시키거나 결제를 다시 기록하지 않는다.

### 6.4 일마감 데이터

일마감은 원본 데이터가 아니라 보고서 형태로 보여준다.

- 총 방문
- 총 매출
- 현금 합계
- 카드 합계
- 자원별 이용 횟수
- 자원별 이용 시간
- 취소 / 노쇼 수

## 7. 보안과 개인정보

### 7.1 접근 분리

- `/kiosk`: 학생/보호자 접근 가능
- `/admin`: 직원 PIN 필요
- `/maintenance`: 관리 책임자 PIN 필요
- DB 파일: 브라우저에서 직접 접근 불가

### 7.2 개인정보 최소 노출

- 보드 화면은 이름보다 번호 표시를 기본값으로 한다.
- 키오스크 검색 결과에는 필요한 회원 정보만 보여준다.
- 관리자 화면에서도 보호자 연락처는 전체 노출보다 마스킹을 우선한다.
- CSV 내보내기는 관리자 PIN 또는 유지보수 PIN을 요구한다.

### 7.3 감사 기록

다음 행동은 반드시 운영 로그에 남긴다.

- 결제 기록
- 이용 시작
- 이용 종료
- 연장
- 호출
- 노쇼
- 재대기
- 설정 변경
- 백업 실행

## 8. 백업과 복구

### 8.1 자동 백업

서버 노트북은 매일 운영 종료 후 DB 파일을 백업한다.

권장 위치:

```text
C:\autoPAN\data\autopan.sqlite
C:\autoPAN\backups\autopan-YYYYMMDD-HHMM.sqlite
```

### 8.2 관리자 화면 표시

관리자 첫 화면에 다음을 표시한다.

```text
DB 정상
마지막 백업: 2026-05-11 20:30
남은 저장공간: 충분
```

### 8.3 복구 원칙

운영자는 직접 복구하지 않는다. 복구는 개발자 또는 관리 책임자가 유지보수 화면과 문서를 보고 수행한다.

## 9. 성공 기준

v2 설계가 완료되었다고 판단하는 조건은 다음과 같다.

- 운영자가 DB를 몰라도 접수부터 종료까지 처리할 수 있다.
- 서버 노트북 재부팅 후 앱이 자동으로 다시 열린다.
- 태블릿과 직원 PC가 전용 공유기 내부망에서 접속된다.
- 하루 운영 데이터가 서버 재시작 후에도 유지된다.
- 관리자 화면에서 백업 상태를 확인할 수 있다.
- `/admin`과 `/maintenance`는 학생이 접근할 수 없다.
- 일마감 데이터를 CSV로 내려받을 수 있다.

## 10. 구현 순서

1. SQLite 기반 영구 저장소를 만든다.
2. 데모 메모리 저장소와 운영 저장소를 명확히 분리한다.
3. 관리자 PIN과 유지보수 PIN을 추가한다.
4. `/admin`을 업무 탭 구조로 재정리한다.
5. `/maintenance`를 만든다.
6. 자동 백업과 백업 상태 표시를 구현한다.
7. Windows 실행 스크립트와 자동 시작 절차를 만든다.
8. 전용 공유기 운영 문서를 작성한다.
9. 키오스크와 관리자 화면을 현재 디자인 시스템에 맞춰 다듬는다.

## 11. 제외 범위

v2에서 하지 않는다.

- 클라우드 배포
- 온라인 결제 연동
- 외부 예약 시스템
- 직원별 복잡한 권한 체계
- 원본 DB 테이블 편집 화면
- 학생용 계정 로그인
- 모바일 앱 별도 개발
