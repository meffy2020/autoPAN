# 나놀다판 운영 자동화 v1 제품 스펙

## 1. 제품 개요

### 1.1 문제 정의

노원청소년센터 나놀다판은 현재 종이 접수증과 수기 스프레드시트 중심으로 현장을 운영하고 있다. 이 방식은 다음 문제가 있다.

- 접수, 대기, 결제, 입장, 종료 정보가 한 곳에 연결되지 않는다.
- 학생이 지금 무엇을 해야 하는지 한 번에 이해하기 어렵다.
- 관리자가 대기열과 현재 이용 상태를 동시에 보기 어렵다.
- 호출과 안내가 사람 의존적이라 누락과 혼선이 생긴다.

### 1.2 제품 목적

이 시스템의 목적은 `키오스크 접수`와 `관리자 운영`을 하나의 흐름으로 연결해 현장 운영을 단순화하는 것이다.

v1의 핵심 목표는 다음과 같다.

- 학생 또는 보호자가 키오스크에서 스스로 접수할 수 있게 한다.
- 유료 콘텐츠와 공간 이용을 명확히 분리한다.
- 유료 콘텐츠는 `즉시 결제 가능` 또는 `대기 등록`으로 단순하게 분기한다.
- 대기 안내는 관리자 화면과 TTS 호출 중심으로 처리한다.
- 관리자는 서울시 결제시스템으로 직접 결제를 진행하고, 그 결과를 운영 흐름에 반영한다.

### 1.3 제품 성격

- 이 시스템은 `운영 시스템`이다.
- 이 시스템은 결제를 직접 승인하지 않는다.
- 실제 결제는 반드시 관리자가 서울시 결제시스템에서 직접 처리한다.
- 이 시스템은 접수, 대기, 호출, 시작, 종료 상태를 관리하는 것이 역할이다.

## 2. 대상 사용자

### 2.1 학생 / 보호자

목표:

- 빠르게 접수한다.
- 지금 어떤 선택을 해야 하는지 바로 이해한다.
- 대기 중이면 호출을 기다리고, 바로 가능하면 관리자 안내를 받는다.

성공 조건:

- `첫 방문 / 재방문`을 쉽게 고를 수 있다.
- 필요한 입력만 단계적으로 보인다.
- 접수 후 다음 행동이 분명하다.

### 2.2 관리자 직원

목표:

- 대기열을 빠르게 관리한다.
- 결제를 서울시 결제시스템에서 직접 처리한다.
- 자원 배정, 시작, 종료, 예외 처리를 최소 조작으로 수행한다.

성공 조건:

- 자원별 대기 상태와 이용 상태가 한눈에 보인다.
- 호출 대상과 즉시 입장 대상을 바로 구분할 수 있다.
- 결제 후 시작 처리까지 흐름이 끊기지 않는다.

## 3. 운영 환경과 자원

### 3.1 운영 자원

- 컴퓨터: 6대
- 닌텐도: 4대
- 플레이스테이션: 2대

### 3.2 운영 화면

- `/kiosk`: 학생/보호자 접수
- `/admin`: 관리자 운영
- `/`: 운영 진입과 요약

### 3.3 운영 방식

- 키오스크와 관리자 화면은 같은 내부망 브라우저로 접속한다.
- 여러 기기에서 동시에 열려 있어도 같은 상태를 봐야 한다.
- 공개 보드는 v1 범위에서 제외한다.

## 4. 핵심 운영 원칙

### 4.1 키오스크는 접수 전용

- 키오스크는 접수만 처리한다.
- 결제는 키오스크에서 처리하지 않는다.
- 키오스크는 학생이 스스로 정보를 입력하고 선택을 완료하는 데 집중한다.

### 4.2 결제는 관리자 직접 처리

- 유료 콘텐츠 결제는 반드시 관리자가 직접 처리한다.
- 결제는 서울시 결제시스템에서만 진행한다.
- 본 시스템은 결제 승인 기능을 가지지 않는다.
- 본 시스템은 필요할 경우 `결제 완료 여부`, `결제 시각`, `관리자 메모` 정도만 운영용으로 남긴다.

### 4.3 유료 콘텐츠와 공간 이용 분리

- `PC`, `닌텐도`, `PS`는 유료 콘텐츠다.
- `공간 이용`은 비유료 방문 기록 흐름이다.
- 공간 이용은 대기열, 결제, 세션 흐름에 들어가지 않는다.

### 4.4 자원 종류별 대기열

- 유료 콘텐츠 대기열은 `PC`, `닌텐도`, `PS`별로 독립된다.
- 각 대기열은 FIFO를 기본 원칙으로 한다.
- 학생은 자원 종류만 선택한다.
- 학생은 대기 시점에 구체 자리를 고르지 않는다.
- 자리가 비면 관리자가 해당 자원 종류의 가장 앞 대기자에게 빈 자리부터 배정한다.

### 4.5 관리자 확정 시작

- 이용 시간은 접수 시점이 아니라 관리자가 시작 처리한 시점부터 계산한다.
- 결제와 실제 이용 시작은 별도 단계다.
- 호출되었더라도 관리자가 시작하지 않으면 세션은 시작되지 않는다.

### 4.6 점진적 공개

- 키오스크는 한 단계에 하나의 선택만 요구한다.
- 이전 단계가 끝나기 전에는 다음 기능을 드러내지 않는다.
- 복잡한 운영 기능은 관리자 화면에만 둔다.

### 4.7 무반응 자동 복귀

- 키오스크에서 30초 이상 입력이나 터치가 없으면 첫 화면으로 돌아간다.
- 모든 버튼 클릭과 입력은 무반응 타이머를 초기화한다.

### 5.1 포함 범위

- 신규 회원 등록
- 재방문 회원 검색
- 키오스크 단계형 접수
- 자원 종류 선택
- 유료 콘텐츠 대기열 관리
- 관리자 직접 결제 후 시작 처리
- 세션 시작 / 종료 / 연장

- 노쇼 처리 / 재대기
- 공간 이용 방문 기록
- 일마감 리포트

### 5.2 제외 범위

- 실제 카드 승인 연동
- 키오스크 결제
- 공개 보드
- 외부 모바일 예약

- 기존 스프레드시트 데이터 이관
- 고도화된 관리자 인증과 권한 체계

## 6. 핵심 사용자 흐름

### 6.1 재방문 접수 흐름

1. 학생 또는 보호자가 키오스크에 진입한다.
2. `재방문`을 선택한다.
3. 이름 또는 보호자 연락처로 기존 회원을 찾는다.
4. 회원을 선택한다.
5. `PC / 닌텐도 / PS / 공간 이용` 중 하나를 선택한다.
6. `공간 이용`이면 방문 기록만 남기고 첫 화면으로 돌아간다.
7. 유료 콘텐츠면 시간권을 선택한다.
8. 시스템은 현재 대기 여부를 판단한다.
9. 대기가 없으면 `관리자 결제 안내` 상태로 넘긴다.
10. 대기가 있으면 대기열에 등록한다.

### 6.2 첫 방문 접수 흐름

1. 학생 또는 보호자가 키오스크에 진입한다.
2. `첫 방문`을 선택한다.
3. 학생 이름, 학년 또는 나이, 보호자 연락처를 입력한다.
4. `PC / 닌텐도 / PS / 공간 이용` 중 하나를 선택한다.
5. `공간 이용`이면 방문 기록만 남기고 첫 화면으로 돌아간다.
6. 유료 콘텐츠면 시간권을 선택한다.
7. 시스템은 현재 대기 여부를 판단한다.
8. 대기가 없으면 `관리자 결제 안내` 상태로 넘긴다.
9. 대기가 있으면 대기열에 등록한다.

### 6.3 공간 이용 흐름

1. 학생 또는 보호자가 본인 정보를 확인한다.
2. `공간 이용`을 선택한다.
3. 시스템은 오늘 방문 기록만 남긴다.
4. 대기열과 세션은 생성하지 않는다.
5. 화면은 첫 단계로 돌아간다.

### 6.4 유료 콘텐츠 즉시 이용 흐름

1. 학생이 `PC`, `닌텐도`, `PS` 중 하나를 선택한다.
2. 해당 자원 종류에 대기가 없으면 즉시 이용 가능 상태로 본다.
3. 학생은 관리자 안내를 받는다.
4. 관리자는 서울시 결제시스템에서 직접 결제를 진행한다.
5. 관리자는 결제 완료 후 자리를 배정하고 시작 처리한다.

### 6.5 유료 콘텐츠 대기 흐름

1. 학생이 `PC`, `닌텐도`, `PS` 중 하나를 선택한다.
2. 해당 자원 종류에 대기가 있으면 대기열에 등록한다.
3. 시스템은 대기번호를 발급한다.
4. 자리가 나면 관리자 화면에서 해당 자원 종류의 가장 앞 대기자를 확인한다.
5. 시스템은 TTS 호출 이벤트를 생성한다.
6. 학생이 오면 관리자가 서울시 결제시스템에서 직접 결제를 진행한다.
7. 결제 완료 후 관리자가 빈 자리부터 배정하고 시작 처리한다.

### 6.6 관리자 운영 흐름

1. 관리자는 대기열 또는 즉시 이용 대상을 확인한다.
2. 관리자는 서울시 결제시스템에서 직접 결제를 진행한다.
3. 필요 시 결제 완료 여부나 메모를 시스템에 남긴다.
4. 사용 가능한 자리를 배정한다.
5. 시작 처리 후 세션을 연다.
6. 필요하면 연장 결제를 다시 직접 진행한다.
7. 이용이 끝나면 세션을 종료한다.

## 7. 예외 흐름

### 7.1 노쇼

- `ready` 상태 학생이 정해진 시간 안에 오지 않으면 관리자가 노쇼 처리한다.
- 노쇼 처리된 학생은 종료하거나 다시 대기열 마지막으로 보낼 수 있어야 한다.

### 7.2 재대기

- 관리자는 운영 판단에 따라 학생을 다시 대기열에 넣을 수 있다.
- 재대기 시 해당 자원 종류 대기열의 마지막으로 들어간다.

### 7.3 결제 후 미시작

- 결제가 끝나도 관리자가 시작하지 않으면 세션은 열리지 않는다.
- 결제와 시작은 반드시 별도 상태로 유지한다.

### 7.4 연장

- 연장은 관리자 직접 결제가 끝난 뒤 처리한다.
- 연장 시 추가 시간과 운영 메모가 남아야 한다.
- 연장 후 종료 예정 시간이 다시 계산되어야 한다.

### 7.5 공간 이용

- 공간 이용은 방문 기록에는 포함된다.
- 공간 이용은 대기열, 세션, 매출, 점유율 집계에는 포함되지 않는다.

### 7.6 키오스크 무반응

- 입력 또는 선택 없이 30초가 지나면 키오스크는 첫 화면으로 돌아가야 한다.
- 자동 복귀 시 미완료 입력값은 버린다.

## 8. 도메인 모델과 상태

### 8.1 핵심 엔터티

- `members`
- `resources`
- `pricing_rules`
- `visits`
- `queue_entries`
- `sessions`
- `payments`
- `tts_events`
- `staff_activity_logs`
- `system_settings`

### 8.2 방문(`visits`)

의미:

- 하루의 실제 방문 단위
- 회원, 자원 종류, 접수 시각을 묶는 상위 기록

상태:

- `queued`
- `awaiting_payment`
- `in_session`
- `completed`
- `canceled`
- `no_show`

메모:

- 유료 콘텐츠는 접수 후 `queued` 또는 `awaiting_payment`로 시작한다.
- 공간 이용은 방문만 생성하고 곧바로 `completed`로 끝난다.

### 8.3 대기(`queue_entries`)

의미:

- 자원 종류별 대기열 순서를 표현하는 단위

상태:

- `waiting`
- `ready`
- `seated`
- `no_show`
- `canceled`

전이:

- `waiting` → `ready`
- `ready` → `seated`
- `ready` → `no_show`
- `no_show` → `waiting`

### 8.4 세션(`sessions`)

의미:

- 실제 자원 사용 시작 이후의 이용 기록

상태:

- `active`
- `ended`

전이:

- `active` → `ended`

### 8.5 결제(`payments`)

의미:

- 외부 결제 시스템에서 관리자가 직접 처리한 결과를 운영용으로 남기는 기록

단계:

- `initial`
- `extension`
- `adjustment`

메모:

- 결제 승인 자체는 본 시스템이 수행하지 않는다.
- 서울시 결제시스템의 결과를 사람이 확인하고 반영하는 구조다.

## 9. 기능 요구사항

### 9.1 회원

- 신규 회원을 등록할 수 있어야 한다.
- 재방문 회원을 이름, 보호자 연락처, 학년/나이 기준으로 검색할 수 있어야 한다.
- 같은 학생의 중복 등록을 줄이는 기준이 있어야 한다.
- 마지막 방문 시각을 기록해야 한다.

### 9.2 접수

- 키오스크에서 방문 기록을 만들 수 있어야 한다.
- 일반 자원 접수는 자원 종류와 시간권을 포함해야 한다.
- 대기 발생 시 대기번호를 발급해야 한다.
- 대기가 없을 때는 즉시 이용 가능 상태로 넘길 수 있어야 한다.
- 공간 이용은 별도 대기번호 없이 방문 기록만 남길 수 있어야 한다.
- 30초 무반응 시 첫 화면으로 자동 복귀해야 한다.

### 9.3 대기열

- 자원 종류별 독립 대기열을 유지해야 한다.
- 빈 자리가 생기면 다음 대기자를 `ready` 상태로 승급해야 한다.
- 관리자는 수동 재호출, 노쇼, 재대기를 처리할 수 있어야 한다.
- 자리 선지정 없이 자원 종류별 FIFO로 운영해야 한다.
- 실제 자리 번호는 호출 이후 관리자가 배정해야 한다.

### 9.4 결제

- 본 시스템은 결제를 직접 승인하지 않아야 한다.
- 결제는 관리자만 처리할 수 있어야 한다.
- 서울시 결제시스템 결제 후 운영 상태를 반영할 수 있어야 한다.
- 연장 결제는 별도 단계로 처리할 수 있어야 한다.

### 9.5 세션

- 시작 시 시작 시각과 종료 예정 시각을 기록해야 한다.
- 자원 ID와 방문 ID가 연결되어야 한다.
- 연장 시 추가 시간을 누적해야 한다.
- 종료 시 실제 종료 시각을 남겨야 한다.

### 9.6 알림

- 입장 가능 시 TTS 이벤트를 생성해야 한다.
- 종료 임박 시 TTS 이벤트를 생성해야 한다.
- 시간 종료 시 TTS 이벤트를 생성해야 한다.
- TTS는 관리자 운영 흐름에서 사용할 수 있어야 한다.

### 9.7 리포트

- 총 매출
- 유료 콘텐츠별 매출
- 활성 세션 수
- 재방문율
- 자원별 대기 건수
- 자원별 이용 시간
- 자원별 점유율
- 공간 이용 방문 수

## 10. 화면별 책임

### 10.1 홈 `/`

책임:

- 오늘 운영 상태를 요약한다.
- 각 운영 화면으로 진입시킨다.

### 10.2 키오스크 `/kiosk`

책임:

- 학생/보호자가 스스로 접수하도록 돕는다.
- 단계별로 한 가지 선택만 강조한다.
- 유료 콘텐츠와 공간 이용을 분기한다.
- 무반응 시 첫 화면으로 돌아간다.

### 10.3 관리자 `/admin`

책임:

- 대기열, 호출, 결제 확인, 시작/종료, 연장, 예외 처리를 빠르게 수행한다.
- 운영자가 판단해야 할 정보를 가장 먼저 보여준다.
- TTS 호출의 중심 화면 역할을 한다.

## 12. 비기능 요구사항

- 내부망 환경에서 안정적으로 동작해야 한다.
- 저사양 서버에서도 운영 가능해야 한다.
- 관리자 화면은 자주 갱신되어야 한다.
- 추후 PostgreSQL 영속 저장으로 확장 가능해야 한다.
- 키오스크는 장시간 켜져 있어도 초기 상태로 회복 가능해야 한다.

## 14. 수용 기준

- 학생 또는 보호자는 키오스크에서 스스로 접수할 수 있어야 한다.
- 키오스크는 한 단계에 하나의 선택만 보여야 한다.
- 유료 콘텐츠는 `즉시 이용` 또는 `대기 등록`으로만 분기해야 한다.
- 결제는 반드시 관리자가 서울시 결제시스템에서 직접 처리해야 한다.
- 접수에서 시작, 종료까지 데이터 흐름이 끊기지 않아야 한다.
- 공간 이용은 일반 대기 흐름과 충돌하지 않아야 한다.
- 키오스크는 30초 무반응 시 첫 화면으로 돌아가야 한다.
